# noet-core Architecture

**Purpose**: High-level overview of noet-core's architecture for developers getting started with the library.

**For detailed specifications**, see [`beliefbase_architecture.md`](./beliefbase_architecture.md).

## What is noet-core?

noet-core is a **multigraph-based knowledge management library** that transforms interconnected documents (Markdown, TOML, etc.) into a queryable graph structure. It maintains **bidirectional synchronization** between human-readable source files and a machine-queryable multigraph, automatically managing cross-document references and propagating changes.

The name "noet" comes from "noetic" — relating to knowledge and the intellect.

## Core Concepts

### Documents → Graph Compilation

noet-core acts as a **compiler** for document networks. Source files are parsed via format-specific codecs into an intermediate representation, references between documents are resolved by the graph builder, and the result is a compiled multigraph (the BeliefBase) that applications can query and traverse.

The pipeline mirrors a traditional compiler: parse → link → emit. Source documents are the "source code," the BeliefBase is the "compiled output," and the graph builder is the "linker."

### The BeliefBase

A **BeliefBase** is the compiled representation of your document network:

- **Nodes** represent documents, sections, or custom entities
- **Edges** connect nodes with typed, semantic relationships
- **Identifiers** give each node a stable UUID-based identity (BID)

The graph is always synchronized with source files — changes flow bidirectionally. Edits to source documents are compiled into the graph, and system-managed metadata (like BIDs and link targets) is written back to source.

### Multi-Pass Compilation

Like a traditional compiler, noet-core handles forward references and circular dependencies through multiple parse passes:

1. **Discovery**: Parse all files, collect unresolved references as diagnostics
2. **Resolution**: Reparse files with resolved dependencies, inject BIDs, create relations
3. **Convergence**: Iterate until all resolvable references are linked

Unresolved references are diagnostics, not errors. The compiler tracks them and resolves automatically in subsequent passes. This means you can reference documents before they're parsed.

### Node Identity: Multi-ID Triangulation

Every node can be referenced through **multiple identity types** that work together:

- **BID**: A globally unique UUIDv6 that survives all changes (renames, moves, title edits). Generated by the system and injected into source file metadata.
- **Bref**: A compact 12-character reference derived from the BID, used in links.
- **ID**: An optional user-defined semantic identifier (e.g., `{#intro}` on a markdown heading).
- **Title**: An auto-generated anchor from the heading text.
- **Path**: The filesystem location (changes on move/rename).

When a user creates a document, the system injects a BID into its frontmatter. If the file is later renamed or moved, the BID remains stable — so any links targeting that BID continue to resolve. Title changes are also safe: the BID is the permanent anchor, and other identity types update around it.

This multi-ID approach gives you stable references (BID/Bref), user-friendly anchors (ID/Title), and filesystem discoverability (Path) — all pointing to the same node.

#### NodeKey String Format

NodeKeys are parsed from strings using a URL-based format. Four schemes
correspond to the four `NodeKey` variants:

| Scheme | Examples | NodeKey variant | Notes |
|--------|----------|-----------------|-------|
| `bid:` | `bid:019722ab-...` | `Bid` | Full UUID |
| `bref:` | `bref:abc123def456` | `Bref` | 12-char hex alias |
| `id:` | `id:my-node` | `Id` | Non-hierarchical (implicit network) |
| `id://` | `id://net-bref/my-node` | `Id` | Hierarchical (explicit network in authority) |
| `path:` | `path:docs/file.md` | `Path` | Non-hierarchical |
| `path://` | `path://net-bref/docs/file.md` | `Path` | Hierarchical (explicit network) |
| *(bare)* | `abc123def456`, `my-node`, `docs/file.md` | *(heuristic)* | See below |

**Hierarchical** (`scheme://authority/path`): the authority component is a
network BID or Bref. **Non-hierarchical** (`scheme:value`): no network;
filled in later by resolution.

**Bare strings** (no scheme) use heuristic parsing: the string is probed
as a BID, then a Bref; if it contains path-like characters (`/`, `#`, `.`)
it becomes a `Path`; otherwise it becomes an `Id`. If the first path
component is a valid BID/Bref, it is extracted as the network.

The canonical `Display` output uses the shortest unambiguous form: `bid:UUID`,
`bref:HEX`, `id:slug` or `id://net/slug`, `path:file` or `path://net/file`.
Round-trip: `parse(display(key)) == key`.

For detailed specifications including collision detection, normalization rules, and storage, see [`beliefbase_architecture.md` § 2.2](./beliefbase_architecture.md#22-identity-management-bid-bref-and-nodekey).

### Link Format: Readable + Resilient

noet-core transforms markdown links to a canonical format that combines human-readable paths with stable Bref identifiers, stored in the CommonMark title attribute:

```
[Link Text](relative/path.md#anchor "bref://abc123def456")
```

The path stays human-readable and portable. The Bref ensures the link survives file renames and moves. When files are reorganized, noet-core automatically updates the paths while preserving the Bref.

Supported input formats include standard markdown links, WikiLinks (`[[Document Name]]`), same-document anchors, and explicit Bref references.

For the full link resolution algorithm, see [`link_format.md`](./link_format.md).

### Relationship Types (WeightKind)

Edges are classified into three infrastructure types:

- **Subsection**: Document structure (heading hierarchy within a document)
- **Epistemic**: Knowledge dependencies (citations, prerequisites, cross-references)
- **Pragmatic**: Domain-specific relationships (application-defined semantics)

Each relationship can carry a `payload` with custom metadata. For the conceptual model behind this classification — including directionality (source/sink/owner), the DAG structure, and how queries compose across edge types — see [`dag_model.md`](./dag_model.md).

### Schema Extensibility

Nodes have an optional `schema` field for domain classification. noet-core is schema-agnostic — you define what schemas mean in your application. This allows the same graph infrastructure to support requirements management, knowledge bases, project tracking, or any other structured document domain.

### Metadata Format Flexibility

Document metadata (frontmatter) supports YAML, JSON, and TOML with automatic format detection. The system tries formats in priority order (YAML → JSON → TOML), so existing documents in any format work without migration. Network configuration files (`BeliefNetwork.yaml`, `.json`, or `.toml`) follow the same convention.

### The API Node

Every BeliefBase has a special **API node** that serves as the graph's root entry point and tracks the noet-core schema version. This enables forward compatibility (older versions can parse newer document trees) and provides a universal anchor for graph traversal. The API node uses a reserved BID namespace that cannot collide with user-created content.

### System Network Namespaces

Beyond user-defined document networks, noet-core maintains three system-managed namespaces:

- **Buildonomy**: The API node itself (schema versioning, graph entry point)
- **Href**: Collects all external HTTP/HTTPS links encountered during parsing, enabling backlink queries, link rot detection, and citation analysis
- **Asset**: Tracks embedded resources (images, PDFs) that noet-core cannot parse as structured documents, enabling asset tracking and completeness checking

These are standard Network nodes — they participate in the same graph traversal and query operations as user-defined networks.

For implementation details, see [`beliefbase_architecture.md` § 2.4](./beliefbase_architecture.md#24-the-api-node-and-system-network-namespaces).

## Architecture Overview

### Components

**BeliefBase** — Core multigraph data structures: the full-featured `BeliefBase` (with indices, query operations, and API node) and the lightweight `BeliefGraph` transport structure.

**Codec** — Document parsing and synchronization: the pluggable `DocCodec` trait, the `DocumentCompiler` (queue-based multi-pass orchestrator), and the `GraphBuilder` (stateful graph construction). Built-in codecs handle Markdown, TOML, and spreadsheets.

**Properties** — Node and edge type definitions: `BeliefNode`, `Bid`/`Bref` identity types, `NodeKey` polymorphic references, and `WeightKind` edge classification.

**Event** — Event streaming for reactive synchronization with graph changes.

**Query** — `QuerySpec`-based graph traversal via the `BeliefSource` trait, with `QueryPackage` lifecycle, tape recording, and view rendering.

**Paths** — Relative path resolution across nested networks.

**Shard** — Per-network BeliefBase export and compile-time search index generation for browser-based viewers.

### Data Flow

```
1. File system changes detected
   ↓
2. DocumentCompiler enqueues modified files
   ↓
3. DocCodec parses file → IRNodes
   ↓
4. GraphBuilder resolves references → BeliefEvents
   ↓
5. BeliefBase updated, events published
   ↓
6. Application reacts to events, queries graph
```

### Extensible Parsing (DocCodec)

noet-core supports multiple document formats through a pluggable codec system. The `DocCodec` trait separates concerns: codecs handle **syntax** (parsing documents into intermediate representation), the `GraphBuilder` handles **semantics** (resolving references, creating relations, managing identity), and HTML generation is **presentation** (codecs return body content, the compiler wraps with templates).

For structured data formats that require context from an owning network codec, a two-registry dispatch system (`WALK_CODECS` + `CLAIM_MAP`) controls which codec handles which file. This is a non-obvious subsystem — see [`beliefbase_architecture.md` § 3.2](./beliefbase_architecture.md#32-the-codec-system-three-sources-of-truth) before implementing new codecs.

noet also extends Markdown with MyST backtick-fence block directives (e.g., `{network_children}`, `{requirements_table}`) that are resolved during the compiler's deferred pass. See [`myst_directive_architecture.md`](./myst_directive_architecture.md) for the directive pipeline.

### Sharding and Search

For large repositories, the export pipeline automatically splits the BeliefBase into per-network MessagePack shards so browser viewers can load data on demand. Compile-time search indices (TF-IDF with English stemming) are always generated per-network, enabling full-corpus search before any data shard is fetched.

See [`search_and_sharding.md`](./search_and_sharding.md) for the full specification.

## Relationship to Prior Art

### Knowledge Management Tools (Obsidian, Roam, Logseq)
✅ Bidirectional linking, graph visualization, Markdown-based
**+** Automatic BID injection for stable references
**+** Multi-format support and nested network hierarchies
**+** Multi-pass forward reference resolution

### Hypergraph Libraries (HGX, HIF)
✅ Directed, weighted hypergraph with multiple relationship types
**+** Document management focus with bidirectional doc-graph sync
**+** Diagnostic-driven unresolved reference tracking

### Knowledge Graph Systems (Neo4j, Docs2KG)
✅ Document → graph construction, multi-format parsing, rich querying
**+** Writes BIDs/links back to source (source documents are authoritative)
**+** Three-way reconciliation (docs/cache/DB)

### Language Servers (rust-analyzer, tree-sitter)
✅ Incremental error-tolerant parsing, diagnostic tracking, file watcher integration
**+** Knowledge management domain
**+** Writes back to source (BID injection) with multi-pass cross-file resolution

## Unique Features

1. **Bidirectional doc-graph sync**: Changes flow both ways — source edits compile into the graph, system metadata writes back to source
2. **Diagnostic-driven compilation**: Multi-pass resolution guided by unresolved-reference diagnostics, not failure
3. **Nested network paths**: Hierarchical document networks with stable BID references across boundaries
4. **Continuous error-tolerant compilation**: Parsing never fails catastrophically; partial results are always available
5. **Dynamic source blocks**: BID injection, auto-title references, and path updates maintain source file integrity

## Optional Features

- **`bin`**: CLI with parsing, HTML generation, and embedded WASM viewer (includes `wasm`, `stemming`)
- **`service`**: File watching, database sync, and HTTP server (native platform only)
- **`wasm`**: WebAssembly target for browser-based viewers (includes `stemming`)
- **`xlsx`**: Spreadsheet ingestion via calamine (non-wasm only)
- **`mcp`**: Model Context Protocol server for AI agent access
- **`git-tracking`**: Git repository metadata injection into BeliefNetwork nodes
- **`server-math`**: Server-side KaTeX math pre-rendering (non-wasm only)
- **`stemming`**: English stemming for compile-time search indices
- **`all`**: Batteries-included alias (`bin` + `service` + `git-tracking` + `mcp` + `xlsx` + `server-math`)

Default features: `bin`, `service`, `git-tracking`, `server-math`.
